# 钨极项目收尾

## 目标

在开发对话结束时，让 Obsidian 和仓库文档只保留当前有效的信息。把文档当作需要持续编辑的知识入口，而不是不断追加的开发日志。

项目目录：`/Users/caye/Projects/macos-dock-cc-v2`

Obsidian 目录：`/Users/caye/Documents/Obsidian Vault/Projects/macos-dock-cc-v2`

## 事实来源

- 以本轮对话、owner 的验收反馈，以及本轮已经产生的提交、测试和工具结果为依据。
- 不重新读取、扫描或分析源代码，也不全面巡检仓库文档。
- 上下文缺少分支、提交号等必要客观信息时，只核对最小范围的 Git 状态或日志。
- 上下文仍不足或相互矛盾时，不猜测、不写入文档；在结果中向 owner 说明。

## Obsidian 文档体系（两级待办）

待办只有两级：① `00 当前进度.md` 首页地图上的待办节点（标题）→ ② `03 待办与想法/待办/` 的待办卡片（唯一的详情载体）。没有独立的分区索引，也不再为复杂任务另开追踪文档——详情一律就地写在卡片里。

先阅读受影响文档的当前内容，再判断哪些职责确实受到本轮变化影响。没有变化的文件不要修改。

### `00 当前进度.md`（首页 · 全貌与检查点地图）

收尾时按需做四件事：① 把 `★ 你在这里` 移到最新检查点；② 把本轮产生的检查点加进对应阶段泳道（带 `↩ / ⇤ 整组 / ⚠ 人工` 回滚标记和 hash）；③ 增删待办节点（新待办加节点、完成或放弃的删节点）；④ 地图下方的「优先做」行随待办增删或优先级变化同步（这行是唯一的优先级视角，地图本身按阶段而非优先级排）。

硬规则：

- 待办节点文字必须与待办卡文件名**完全一致**——点击跳转和悬停预览靠 `internal-link` class 按节点文字解析。节点文字不加 ⬜/🐛 等前缀，类型靠配色 class（pending / bug / wip）。
- 不得删除图中的 `class … internal-link` 声明行；不得改用 `obsidian://` 的 `click` 指令（Obsidian mermaid 安全模式会拦截）。
- 待办卡改名时，必须同步地图节点文字（以及「优先做」行里可能存在的同名链接）。
- 提交的回滚可行性发生变化（新冲突、组合并、封存或找回）时，同步仓库 `Docs/23-rollback-ledger.md` 回滚账本。
- 顶部首页简介与入口行只在文档结构或入口变化时更新。

### 待办卡片

- 新待办 = 两件套：`03 待办与想法/待办/` 建卡（frontmatter：阶段 / 分区 / 状态 / updated）+ 地图对应泳道加节点。不再写分区索引行。
- 卡片是 owner 与 agent 唯一的协作面：任务的目标、范围、计划、进展和验收**就地改写**在卡里。简单任务几句话写清目标和完成判定即可；复杂任务就地展开成带任务清单 / 分步计划的长文档（现例：`代码质量优化.md`）。任务从简单长成复杂就在原卡扩写，不另开中转或追踪文档。
- 完成或明确放弃 = 卡片移入 `Archive/已完成待办/`（目录不存在则创建；状态改 ✅ 或 ✂️，写完成日期）+ 删地图节点 +（若在「优先做」行）删该链接。用户可见功能必要时微调该泳道绿牌概括（`02 已完成功能清单.md` 已归档，不再逐条登记）。

### 产品决策与流程踩坑（2026-08-01 起在仓库，不再写进笔记库）

这两类内容的读者是 agent 而不是 owner，已搬进仓库。收尾时**按需直接更新，不等口令**：

- `Docs/27-product-decisions.md`：当前有效产品共识的总结，不是决策日志。优先改写、合并或删除现有内容，不在末尾持续追加；同一主题只保留当前结论，决定反转后用新结论替换旧结论；只保留长期影响产品判断的原则，不记录实现细节、讨论过程、提交记录和普通小改动。**约束本身写 `AGENTS.md`，这里只写理由和反转史**，同一结论不两边都写。
- `Docs/28-process-pitfalls.md`：只记**工作方式**上的跟头（分支、打包、验收、版本），不记应用毛病（写 bug 卡片）和代码实现层的坑（写 `Docs/` 其他文档）。三条同时成立才补：不读代码的人也会踩、会重复发生、这次已真的浪费过时间。没踩坑就不动它——默认不写。
- `02 已完成功能清单.md` 已归档到 Obsidian `Archive/2026-08-01 文档瘦身/`，**不再维护**；已完成功能只体现在地图泳道的绿牌概括里。
## 仓库文档职责

只有本轮上下文明确表明某项职责发生变化时，才读取并更新对应文件。不要为了收尾而遍历所有文档。

- `AGENTS.md`：只记录新的或发生变化的工程硬约束，并且该约束必须能防止未来代码回归。合并或替换旧规则，不记录项目进度、路线图、决策过程和提交历史。
- `Docs/`：只更新与本轮变化直接相关的平台事实、调试方法或需要长期复用的深入工程参考；`Docs/23-rollback-ledger.md` 与首页地图同步维护。现行参考留在根目录；历史调查资料放入 `Docs/Archive/`。不要重写已有归档。
- `README.md` 与 `README.zh-CN.md`：只记录 owner 已确认需要公开的功能、安装方式、系统要求和用户使用方法。任一版本需要更新时，中英文必须同步；未发布实验分支不自动写入。
- `CLAUDE.md`：连接器 + 「本项目覆盖」块。仅在 `AGENTS.md` 的引用方式、Obsidian 路径入口，或本项目的文档分工规则发生变化时更新。
- `Docs/README.md`：仅在活跃 Docs 的结构或索引发生变化时更新。

## 严格边界

- 项目收尾时禁止读取或修改 `03 待办与想法/灵感速记.md`。owner 以后明确要求整理速记时，将其作为独立任务处理，不属于本 skill。
- 不修改 Obsidian Archive（把完成的待办卡移入 `Archive/已完成待办/` 是唯一例外）、推广资料或个人笔记。
- 不创建新文档，除非是新待办卡片，或本轮上下文明确产生了无法归入现有文档的长期知识，并且其职责和位置已经确定。
- 不因为触发了 skill 就强行产生文档变更；没有新事实时直接报告无需更新。
- “收尾”不等于提交代码。只有 owner 明确说“打检查点”时，才按 `AGENTS.md` 创建本地提交；不要推送。

## 编辑与验证

1. 根据文档职责就地改写，删除过期或重复内容，避免同一事实在 Obsidian 和仓库文档中重复维护。
2. 使用明确日期；不要用“今天”、“最近”等相对时间描述项目状态。
3. 检查被修改 Markdown 的链接、标题和路径；改了地图待办节点时，核对节点文字与卡片文件名一致，并检查「优先做」行是否需要同步；README 有变化时检查中英文内容对齐。
4. 确认灵感速记未被读取或修改，业务代码没有因收尾流程产生额外变化。
5. 用中文简要报告改了哪些文档；没有修改时明确说明原因。
