## 分支与发布

**发布分支手工挑提交，一定会漏。**
修好的功能像是"又坏了"，实际是那段代码从没进过发布分支——发布分支从更早的位置手工挑了几个提交拉出去，漏掉两个功能提交，日常用的包因此一直缺它们。
→ 开发布分支**从主线直接拉**；万一手工挑了，拉完对一次差异。（2026-07-20 吃过）

**发布之后主线的版本号不动，于是"用户装的包"和"我这台机器上跑的包"版本号一模一样。**
用户报「菜单里没有『打开系统 Dock 设置…』」，我这边打开菜单明明有，两边版本号都显示 `0.6.6 (7)`——光看版本号完全查不出差别。实际是那个功能的提交比发布晚了 14 小时，从没进过任何安装包。整轮排查都花在确认"到底是不是同一份代码"上。
→ 遇到「用户说没有、我这儿有」这类问题，**先比对提交，别信版本号**。要根治就在发版后顺手把内部构建号往前推一位（版本名不变），让开发构建显示 `0.7.0 (9)`、用户装的是 `0.7.0 (8)`，一眼可分。（2026-07-29 吃过）

**提交被"回摘"到新分支后，旧编号就失效了。**
回滚账本里如果记的还是旧编号，将来照着撤销会落空。
→ 回摘后在账本里记**新编号**，并注明原编号可追溯。

**回退重建时只顾着"功能加回来了没有"，会把和故障无关的基建一起丢掉。**
从 v0.6.5 一点一点重建时，注意力全在产品功能上，结果签名+公证打包链、配套的权限重授权引导、试用包脚本这些**跟当初那次故障毫无关系**的东西留在了废弃分支上没跟过来。等到发现，v0.6.6 已经以未签名未公证的形式发出去了，用户得右键才能打开——而这套东西当时明明已经做好了。
→ 回退之前先把要重建的清单列全，**分两类**：出问题的功能，和被顺带牵连的基建（打包、签名、权限、脚本、工程配置）。第二类最容易漏，因为它平时不出现在界面上。重建收尾时对着两条线各点一次名。（2026-07-26 吃过）

**笔记里写"不采用"，代码里它还在跑——两边会悄悄漂移。**
进度笔记把一个修复标成了「owner 不采用」，实际那个提交一直在主线里，连已发布的版本都含着它。这种矛盾平时看不出来，等到要基于笔记做决定时才会误导人。
→ 涉及"某个东西到底采没采用"的结论，写进笔记前先在代码里确认一次；发现两边打架时**先问清楚，不要自行判断哪边对**。（2026-07-26 吃过）

## 打包与安装

**修完不重新打包，等于没修。**
日常在用的包落后于代码时，报上来的 bug 可能早就修好了，白查一轮。
→ 修完一批就换包；报 bug 前先确认手上的包是不是最新的。（2026-07-20 吃过一次完整的）

**日用一定要用 Release 包，Debug 包只配用来验证功能对不对。**
开发用的 Debug 包没有编译器优化，体积是 Release 包的两倍多（实测 16.9 MB 对 7.1 MB）。功能测试用它没问题，但**手感会明显变差**——最小化这种时序和动画敏感的动作尤其明显。2026-07-26 就吃过一次：感觉最小化手感不对，以为是新版本引入的回归，想退回旧版本；查下来 v0.6.5、v0.6.6 和当前主线的最小化代码**是同一份**，退回去根本不会有变化，真正的差别是手上那个包是 Debug 编的。换成 Release 包，手感立刻回来。
→ 拿手感说事之前，先确认手上的包是 Release 还是 Debug；日用一律换成 Release 包。（2026-07-26 吃过）

**复制应用包不能用命令行的普通复制。**
普通复制不保留应用包里的符号链接，装完签名校验直接失败，应用可能起不来或权限失效。
→ 用访达拖拽是安全的；命令行必须用 `ditto`。

**「系统设置里开关是开的」完全不能证明权限生效。**
2026-07-29 折腾了很久：辅助功能列表里钨极的开关明明开着，应用就是拿不到权限；关开一次没用、删掉重加也没用（而且应用还在运行时减号是灰的，必须先退出才能删）。真相是**权限记录会随签名变化不断累积**——本机清理时一口气清出了 **32 条**，你看到那条开着的，属于其中早已失效的某一条。
→ 判断权限有没有真生效，**看应用是不是处于无程序坞图标的模式**（有权限才会切过去），别看开关。彻底修法是把该应用的权限记录整个清空再重新授权一次。（2026-07-29 吃过）

**日常包必须用固定证书签名，不能用临时签名。**（实测结论，别再试临时签名）
临时签名（ad-hoc）没有稳定身份，系统只能拿每次构建都变的指纹当身份，**每装一次新版授权就失配一次**——这就是上面那 32 条记录的由来，也是所有用户升级后权限失效的原因。换成固定证书后实测：指纹从 `c043dc7a` 变到 `2e84976f`、构建号 9→10，**授权依然有效**。
→ 本机日常包一律用 `Scripts/install_local_release.sh` 装（Release + 固定证书 + 装进「应用程序」），授权一次即可长期有效。（2026-07-29 实测确认）

**两个包的辅助功能授权是各自独立的，别以为授权过一次就到处都算数。**
开发构建和 `/Applications` 里的正式包，路径不同、签名也不同，**在系统眼里是两个应用**。给其中一个授权不会覆盖另一个。2026-07-29 就卡在这儿：换完正式包后应用起不来，一时分不清是"权限没给"还是"给错了应用"。
→ 遇到权限问题先确认**现在跑的是哪个包**（菜单版本行会标：带「· 开发版」的是开发构建，不带后缀的是 `/Applications` 正式包），再去看那个包的授权。（2026-07-29 吃过）

**自签名证书只要固定住，辅助功能授权就不会丢。**（正面经验，别忘）
以前每次升级授权就失效——因为签名身份每次构建都在变，系统当成了新应用。现在预览包锁定同一张证书，授权跨版本延续，升级不用重新授权。2026-07-20 实测验证。

**连着重装很多次，会把辅助功能授权弄成一条"看着是开的"死条目。**
为了做 A/B 对照，一天内重装了 5 次、反复启停 20 多次，之后应用起来了却进不了常驻状态——任务条不工作。而系统设置里那个开关**看着还是勾着的**，系统记录里那条授权也还写着"已允许"。它已经和新装的包对不上了。
→ 连续重装做对照之后，如果应用起来了却不干活、又不报错，**先怀疑授权，别去查代码**。修法：完全退出应用（运行中系统设置里的「−」是禁用的）→ 系统设置删掉那条 → 从 `/Applications` 启动 → 重新勾选。（2026-07-31 吃过）

## 验收方式

**验收前先确认只有一个实例在跑。**
上一轮的旧实例常驻后台不会自己退出，新包起来后屏幕上会同时有两个任务条，长得一模一样。这时候你测到的是哪个版本，谁也说不清——2026-07-21 就因此把一个其实没验证过的修复判成"不行"并整个回退，白折腾一轮。
→ 起新包前先扫一遍残留进程，关干净再起；报"不行"之前先确认屏幕上只有一个任务条。（2026-07-21 吃过）

**跑了很久的实例，不能拿来当性能基线。**
同一份代码，挂了几个小时的实例空闲 CPU 是 4.40%，刚起来 90 秒的是 2.60%。第一次对比拿"跑了几小时的旧版"去比"刚装好的新版"，算出降了 68%——**高估**；两组都用刚起来 90 秒的状态重测一遍，真实是 46%。连带那个"内存从 50M 降到 28M"的改进也是假的，配对后两组都是 28M。
→ 性能前后对比，两组必须同预热时长、同一天、同一台机器同样负载；跑了很久的实例只能自己跟自己比。（2026-07-31 吃过）

**只启动一次，验收不了启动期的问题。**
有个约五分之一概率的启动崩溃，在代码里躺了很久都没被发现——因为日常用法是开机启动一次、然后一挂几小时，撞上了也只当是"这次没起来，再点一下"。它最后是做别的实验时顺带撞出来的，不是测出来的。
→ 凡是改动**启动流程、面板创建、窗口布局**的，验收要**连续启动十几次**，别只启动一次就算过。判定"这次起来了"要看应用有没有真进入常驻状态，光看进程还在不算。（2026-07-31 吃过）

**程序模拟的点击，验证不了真实交互。**
合成的点击不携带真实交互凭证，系统对它和真人点击的处理不同——好几个方案在模拟测试里被误判成"无效"，真人一点其实是好的（反之亦然）。
→ 凡涉及焦点、点击、权限的修复，**最终必须真人点一遍**才算验收通过。
