# 26 · 空闲期三个后台轮询：现状核实与设计存档

> **这不是待办。** 前台轮询与最大化避让的降频**已被 owner 决策否掉**（2026-07-31：不拿可感知延迟换空闲 CPU，见 `27-product-decisions.md`）。本文档存的是「若将来改主意」的设计，以及一批已经核实过的硬约束——省得下一轮从零重来。
>
> 唯一还活着的待办是角标的**零感知门控**（不违反那条决策），卡片见 Obsidian `03 待办与想法/待办/没有消息应用时暂停角标轮询.md`。
>
> 背景：`683f1fc` 已把空闲 CPU 中位数从 2.60% 降到 1.40%（−46%，同日配对实测），做法是消掉 2 Hz 的无条件 `@Published` 发布。本文档讲的是**剩下**的部分。

## 现状表

CPU 样本占比来自 owner 侧 profile（互斥分类，非 inclusive 调用栈）。

| 轮询 | 频率 | 空闲期实际动作 | CPU 样本 | 代码位置 |
|---|---|---|---:|---|
| 最大化避让 · 全局扫描 | 5 Hz | detached task 查整屏窗口列表；托举中额外拉一次 `.optionAll` 全量列表 | 11.0% | `WindowLiftAvoidanceController.swift:386`，`:53-56` |
| 最大化避让 · tracked probe | **20 Hz**（有 session 时） | 见下方「第一版错误 ①」 | 含在上行 | `WindowLiftAvoidanceController.swift:488` |
| 前台窗口轮询 | 2 Hz | `.optionAll` **全量**窗口列表（含屏外）+ 前台 app 完整座位对账 | **16.4%** | `AppTracker.swift:997` |
| 消息角标 | 2 Hz | 走一遍系统 Dock 的 AX 树 | 1.9% | `BadgeStore.swift:21` |

三项合计 29.3% 样本、理论上限约 **1.23 个百分点**——单靠它们撑不起「5% → 3.5%」这类目标。任何一轮重启这个话题，先把这个天花板算进去。

## 一、最大化避让

### 硬约束（已核实，不是推测）

- **`appReassertWindow = 1.0s`（`WindowLiftAvoidance.swift:33`）是时间尺度判定的核心。** 轮询周期一旦逼近 1 秒，应用抢顶就可能发生在两次采样之间、被误判成「新的用户会话」——正是 AGENTS 点名不许破坏的 L↔M 缩放记忆死锁。
- **`standoffRounds` 是事件驱动的**（观察到铺满在 `appReassertWindow` 内重现才 +1），不按 tick 计数 → 改周期**不会**改变退让上限的实际含义。
- **有 session 时另有一个 20 Hz 的 tracked probe**（`trackedSessionProbeInterval = 0.05`，`WindowLiftAvoidance.swift:26`）。对日常挂着最大化窗口的用户，常驻成本是它，而慢档**对它完全无效**。

### 修正后的设计（若将来实施）

- 慢档取 **0.4s**，不是 0.6s
- `states` / `suppressedFrames` 任一非空即回 0.2s
- **20 Hz tracked probe 完全不动**
- 异步扫描创建或结束 session 后必须**立即重排计时器**，不能等下一个旧节奏 tick

### 代价与结论

初次抬升平均多等约 0.2s、最差 0.4s；叠加 0.5s 动画后最差完成接近 1.1s。**收益有限而手感变化明确——只值得做保守 A/B，不值得直接落地。**

## 二、前台窗口轮询（三项里最值得做的一项）

### 注释债（可随手修，无行为影响）

`AppTracker.swift:989` 写着「单窗口 app 无歧义，直接跳过，平时零开销」——**这条注释是过期的**。原始实现（`88fef1d`）确实有 `app.windowOrder.count > 1` 这个跳过，inventory-first 重写时丢了，注释留了下来。今天它对单窗口前台 app 也是全量跑，**不存在"零开销"**。

### 硬约束

- **不能把 `windowOrder.count > 1` 搬回来。** 今天一个原生标签组 = 一个座位，搬回来会让 Ghostty 类切标签失效。
- **`captureOnScreenWindowIDs()`（`CGWindowSnapshot.swift:16-24`）查询失败时 `return []`**，与"真的没有 layer-0 窗口"无法区分。连续两次失败会读到"空 == 空"而错误跳过完整对账。要用它做判据，**必须先把返回值改成可选**，把失败与空集分开。
- **`reconcileSeats` 远不只是标题。** 它同时承载最小化状态、shadow pool 轮次（AGENTS 要求判定用**上一轮**的池）、`formerCgIDs` 与 CG 全表求交清理、屏外关闭、phantom 判定输入。放宽它的节奏 = 把这些一起放宽。

### 修正后的设计（若将来实施）

- 每 tick 保留 0.5s 的 on-screen 便宜信号（**切标签响应不变**）
- 完整对账兜底取 **1 秒**（不是 2 秒），且按**单调时间**判断而非 tick 数
- **四者任一都必须走完整 capture**：前台 pid 变化 / on-screen 集合变化 / 快速查询失败 / 距上次完整对账满 1 秒

## 三、消息角标

### 硬约束

`BadgeStore.swift:5` 的注释明确写着产品要求：**清掉未读角标必须即时**。

### 修正后的设计

**只做零感知门控**：任务条逻辑隐藏、或没有可见消息入口时暂停轮询，恢复显示时立即读一次；可见状态下保持 0.5s，**不做退避**。

收益天花板约 0.08 个百分点，优先级最低。

## 四、第一版设计的三处实质错误（本文最有价值的部分）

这三条都是 Codex 评审指出、经核实成立的。写下来是为了下一轮不重犯。

**① 避让：频率表整个漏了 20 Hz 的 tracked probe。**
只看到 5 Hz 全局扫描就去设计慢档，而对日常挂着最大化窗口的用户，常驻成本恰恰是那个 20 Hz probe，慢档对它无效。**教训**：给一个子系统做降频前，先把它**所有**计时器列全，别只抓最显眼的那个。

**② 前台：把「跳过完整对账」轻描淡写成"标题兜底"。**
实际放宽的是最小化状态、shadow pool、`formerCgIDs` 清理、屏外关闭、phantom 判定一整套。**教训**：一个函数叫 `reconcileSeats` 就别当它只做一件事——先读它到底改了哪些状态，再谈能不能少调。

**③ 角标：变化率退避建立在一个错误假设上。**
原话是「清红点总跟在激活该 app 之后，所以前台切换这条钩子正好守住产品要求」。**这是错的**：后台同步、另一台设备已读、应用后台处理都会清角标，与前台切换无关。而且"立即读一次"还可能抢在应用真正清除之前，随后仍要再等一个退避周期。**教训**：把"用户行为总是伴随 X"当成守卫条件之前，先列全不经过 X 的路径。
